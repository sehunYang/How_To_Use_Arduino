## RALPLAN-DR Summary

### Principles

1. **결정론이 곧 신뢰다.** 같은 입력에는 항상 같은 결과. 매칭 실패조차 예측 가능한 경로여야 한다.
2. **콘텐츠와 코드는 분리한다.** 센서·레시피 추가에 코드 변경이 필요하면 실패한 설계다. **부품별 지식(주소 체계·Wokwi 파트·핀맵·소비전류)은 전부 데이터에 있어야 하며, 검증기와 생성기는 그 데이터에 대해 일반적이어야 한다.**
3. **자동화되지 않은 검증은 존재하지 않는 검증이다.** 44건 전건에 기계 검사가 매핑될 때만 참이다. **사람의 판단이 필요한 항목은, 그 판단이 *일어났는지*를 기계가 검사한다.**
4. **모바일이 기본형, 데스크톱이 확장.** 하나의 상태 기계, 두 레이아웃.
5. **보안 규칙이 유일한 방어선.** 규칙을 우회하는 자격증명은 설계·문서화·범위 축소 없이 존재해서는 안 된다.

## 핵심 아키텍처: 검증 원장

> **Revision 1의 근본 결함**: 콘텐츠 정본은 Firestore인데 CI는 git 사본을 검증했다. 교사가 `/admin`에서 코드를 고치면 학생은 고친 코드를 받고 CI는 낡은 사본을 영원히 통과시킨다.

**CI가 밀지 않고 당긴다.**

```
Firestore (정본)                      CI (15분 큐 드레인 + 일일 크론 + PR)
  recipes/{id}                          │
    sketch, wiring[], tunables  ──읽기──▶│  published 공개 + admin/CI는 draft도
  verifyRequests/{recipeId}   ──읽기──▶ │  ← /admin "검증 요청"이 큐에 넣음 (15분 크론이 드레인)
  events (증분: at > cursor)  ──읽기──▶ │  ← 전량 재읽기 금지. 커서 이후만
                                         ├─ sketch → sketches/ 추출
                                         ├─ wiring[] + sensors.wokwi → diagram.json 생성
                                         ├─ L1 정적 (per-recipe) · L2 컴파일 · L5 로직   ← 매일 + 큐
                                         ├─ L3 Wokwi (변경분 매일 / 전량 월 1회)
                                         ├─ events 증분 집계 → stats/{recipeId}          ← 매일
                                         │
  simStatus/{recipeId}         ◀──쓰기───┤  전용 CI 아이덴티티. recipes 는 못 건드림
    { verifyHash, compilePass,           │  ⚠ 최상위 컬렉션. meta/ 하위가 아니다
      simPass, logicPass,                │
      staticIssues[], verifiedAt }       │
  stats/{recipeId}             ◀──쓰기───┤  { started, completed, dropAtStep{}, 
    + processedThrough (커서)            │    processedThrough }
  verifyRequests/{recipeId}    ◀──삭제───┘  처리 완료 시 큐에서 제거
```

**게시 전 검증 경로 (E3 — Phase 4 착수 전 확정 필요)**
정적 페이지는 CI를 직접 트리거할 수 없다. `workflow_dispatch` API는 `actions:write` PAT를 요구하는데, 그것을 클라이언트 번들에 두면 **ADR이 거부한 Admin SDK 키보다 더 나쁜 자격증명**을 모든 방문자에게 넘기는 셈이 된다. 채택안:

> `/admin`의 "검증 요청"이 `verifyRequests/{recipeId}` 문서를 쓴다 → **15분 주기 크론**이 큐를 드레인해 해당 레시피만 L1+L2+L5를 돌리고 `simStatus`를 갱신한 뒤 큐 항목을 삭제한다. 새 자격증명이 필요 없고 서버도 필요 없다.
> **`PL6`의 150분에는 검증 왕복 1회(최대 15분)가 포함된다.**

대안: (b) 24h 지연을 수용하고 `PL6`을 "게시 가능 상태까지"로 재정의 / (c) Cloud Function 1개 도입 (분기 ②의 부분 반전, Follow-up에 이미 예고됨). **Phase 4 착수 전에 셋 중 하나를 확정해 이 절에 기록한다.**

이 구조가 해소하는 것: `sketches/` 수기 유지 폐지(이중 정본 소멸) · `diagram.json`을 `wiring[]`에서 생성(배선도-회로 불일치 불가능) · `simVerified`가 CI 소유 사실 · `recipes` 쓰기 주체는 관리자 1명 유지(Principle 5) · `stats`가 클라이언트 쓰기 경로에서 제거됨.

```
function isAdmin() { return request.auth != null && request.auth.token.admin == true; }
function isCI()    { return request.auth != null && request.auth.token.ci    == true; }

match /recipes/{id}          { allow read: if resource.data.status == 'published'
                                            || isAdmin() || isCI();      // ← N6
                               allow write: if isAdmin(); }
match /sensors/{id}          { allow read: if true;  allow write: if isAdmin(); }
match /meta/{doc}            { allow read: if true;  allow write: if isAdmin(); }
match /simStatus/{recipeId}  { allow read: if true;  allow write: if isCI(); }
match /stats/{recipeId}      { allow read: if isAdmin(); allow write: if isCI(); }
match /verifyRequests/{id}   { allow create: if isAdmin();
                               allow read, delete: if isCI(); }          // ← E3 큐
match /events/{id}           { allow create: if validEventPayload();
                               allow read: if isAdmin() || isCI();       // ← E1 크론 집계
                               allow update, delete: if false; }
```
- ⚠️ **`isAdmin()`은 `uid == ADMIN_UID` 비교가 아니라 커스텀 클레임 방식**이다(명세서 서술과 다름 — 개정 요청 3의 6번). `admin`·`ci` 두 클레임 모두 **로컬에서 Admin SDK로 1회 발급**한다

```
// Storage
match /wiring/{f} { allow read: if true;
                    allow write: if isAdmin()
                                 && request.resource.size < 5*1024*1024
                                 && request.resource.contentType.matches('image/.*'); }
```

## Pre-mortem (4 시나리오)

**1. 검색이 학생 어휘를 못 맞춘다** — 교사가 사전과 테스트 문장을 모두 써서 측정 도구가 같은 편향을 공유한다. 83%는 도달되고 의미는 없다.
*지표:* 학생 작성 문장 0건. *완화:* `PL8`을 Phase 0 게이트로, **학생 작성 15개 + 홀드아웃 15개(튜닝 금지)**, 양쪽 임계치 게이트.

**2. 보안·비용 사고** — 웹 API 키가 번들에 있어 `events`가 자명하게 노출. 규칙은 **속도 제한을 못 하고** 스키마 검사는 필드 모양만 막는다. 오염된 이벤트가 대시보드를 왜곡해 **교사가 멀쩡한 레시피를 고친다.** 예산 알림은 지출을 차단하지 못하고 지연된다.
*지표:* App Check가 "남용 확인 시" 목록에 있음. 규칙 배포 수동. *완화:* App Check day-one + fail-open 정책, 규칙 배포 CI 자동화 + diff, `stats` 클라이언트 쓰기 제거, 일일 백업 + **복원 훈련**.

**3. 저작이 좌초한다** — `focus` 좌표를 숫자로 입력하게 만든다. 레시피당 28개. 3건 만들다 지친다.
*지표:* 4.3에 드래그 대신 숫자 폼. 1.5 결과 240분 초과. *완화:* 드래그 필수, **1.5 종이 도그푸딩(트립 240분)**, `PL6` 2건 실측, 회귀 2회 상한.

**4. 출시 후 콘텐츠 회귀** — 교사가 `/admin`에서 스케치를 고친다. 앵커가 어긋나거나 배선 텍스트가 이미지와 안 맞게 된다. **커밋이 없으므로 CI가 안 돈다.** 교실의 학생 30명이 틀린 배선을 따라한다.
*지표:* 검증이 커밋 트리거에만 걸림. 배지가 해시 게이트 없음. *완화:* **검증 원장** + **일일 크론에 L1·L2·L5 포함** + **해시 게이트 배지** + **게시 전 검증 경로** + L1 #7·#11.

## ADR

**Decision** — GitHub Pages에 배포되는 Vite+React SPA가 Firebase를 브라우저에서 직접 호출하는 서버리스 구조. 콘텐츠는 Firestore가 정본. 검색 인덱스는 **빌드 타임 번들 스냅샷 + Firestore 백그라운드 갱신의 이중 티어**. 검증은 **CI가 Firestore에서 콘텐츠를 당겨** 정적·컴파일·시뮬·로직 4계층으로 수행하고 `simStatus` 원장에 기록하며, **학생 배지는 클라이언트 해시 대조로 게이트**된다.

**Drivers** — 저작 반복 비용 / 하드웨어 없는 회귀 검출 / 정적 배포 하의 즉시 반영

**Alternatives considered**
- Next.js SSR + App Hosting — GitHub Pages 확정으로 구조적 배제
- 빌드 타임 정적 단독(C) — 즉시 반영 파손. **이중 티어(D)가 C의 이점만 흡수**
- recipes 전량 쿼리(B) — 캐시 적용 시 재방문은 대등하나 **캐시 없는 첫 방문**에서 34문서 왕복이 첫 화면을 지배
- Cloud Functions 인덱스 트리거 — 저자 1명 상황에서 인프라 비용 미정당화. 단 드리프트는 예상 이벤트이므로 크론으로 탐지 격상
- **CI가 Admin SDK로 `recipes`에 직접 쓰기** — 규칙 전면 우회 자격증명 필요, Principle 5와 충돌. **`simStatus`/`stats` 전용 CI 아이덴티티로 대체**
- **클라이언트 증분 `stats` 카운터** — 미인증 쓰기 경로가 남고 devtools로 조작 가능. **크론 집계로 대체**
- 34건 전량 실물 검증 — 인터뷰에서 명시적으로 철회

**Why chosen** — 서버 부재가 대부분을 결정했다. 남은 자유도는 "콘텐츠를 어디에 두고 어떻게 읽고 어떻게 검증하는가"였고, 이중 티어 인덱스가 **첫 화면 0 읽기 · 즉시 반영 · 네트워크 장애 내성**을 동시에 만족하는 유일한 조합이었다. 검증 원장은 "정본은 Firestore인데 CI는 git 사본을 본다"는 근본 결함을 제거한다 — 이것이 없으면 네 검증 계층 전체가 학생이 받지 않는 산출물에 대한 진술로 전락한다.

**Consequences**
- **긍정:** 서버 운영비 0원. 개인정보 미수집 유지 → 학교 심의 불필요. 센서 추가가 데이터 추가로 완결(주소 체계·Wokwi 서술자 포함). 배선 뷰어 단일 상태 기계. 네트워크 장애에도 검색 동작. 배지가 구성상 정직.
- **부정:** 규칙이 유일한 방어선이라 규칙 실수의 폭발 반경이 크다. 인덱스 갱신이 클라이언트 책임(일일 탐지로 완화). **GCP 예산 알림은 지출을 차단하지 못하며 하드 캡은 배제한 Functions를 요구한다 — 알림 전용을 수용.** TCA9548A 의존 2건 시뮬 미커버. 딥링크가 HTTP 404 상태로 응답(SPA 폴백의 정상 동작). 대시보드가 최대 24h 지연. 번들 인덱스가 최대 24h 낡을 수 있음(크론이 인덱스 해시 변경 시 Pages 재빌드 트리거).
- **중립:** 총 저작 공수 85~135시간은 **계획의 자체 추정**이며 명세서에 근거가 없다. `PL6` 실측 후 재확정한다.

**Follow-ups** — 다중 저자 → 인덱스 갱신 Functions 승격 / 45~60건 → SVG 렌더러 전환 / TCA9548A 칩 → 34/34 / 진도 코드 내보내기 / 지출 하드 캡 필요 시 빌링 킬스위치 Function 1개
