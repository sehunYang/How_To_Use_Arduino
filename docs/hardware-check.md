# 센서 실물 점검 절차

시뮬레이션은 스케치와 배선 논리가 맞는지는 확인해 주지만, **실물 부품이 데이터시트대로 동작하는지는 확인하지 못합니다.**
예를 들어 BME280으로 팔리지만 실제로는 습도가 없는 BMP280인 모듈, 주소가 다른 보드, 잡음, 클론 칩이 그렇습니다.
이 절차는 그 마지막 차이를 **센서 종류마다 한 번** 메웁니다.
레시피 100여 개가 센서 10종을 나눠 쓰므로, 10번 점검하면 대부분의 하드웨어 위험이 확인됩니다.

## 준비물

- Arduino Uno와 USB 케이블, 브레드보드, 점퍼선
- 점검할 센서 모듈. 실제 수업에 쓸 것과 **같은 판매처·같은 모델**이어야 합니다.
- 기준 도구: 얼음물 컵, 30 cm 이상 자 또는 줄자, 수평한 책상, 100 Ω 저항(5% 이내)과 5 V 전원, 자석, 손전등

## 공통 절차

1. `hardware-check/probes/<센서>/<센서>.ino`를 Arduino IDE로 엽니다.
2. 아래 표의 핀으로 배선하고 업로드합니다.
3. 시리얼 모니터를 엽니다. 보드레이트는 표를 따릅니다.
4. 표의 **조건**을 만든 뒤, 화면에 나온 내용을 처음(`# PROBE ...` 줄)부터 **전부 복사**합니다.
5. `hardware-check/records/<센서>/<조건>.csv`로 저장합니다. 예: `hardware-check/records/ds18b20/ice-water.csv`
6. 모든 조건을 기록했으면 판정합니다.

```bash
npm run verify:hardware                    # 기록된 것만 판정
npm run verify:hardware -- --require-all   # 빠진 조건까지 실패로 처리
```

각 항목이 `PASS`, `WARN`, `FAIL` 중 하나로 표시됩니다. `FAIL`이 하나라도 있으면 그 부품으로는 레시피 결과를 믿을 수 없습니다.
`WARN`은 레시피를 고치거나 학생 안내가 필요한 차이입니다.

기록 파일은 저장소에 커밋해 두세요. 다음에 부품을 새로 살 때 같은 절차로 비교할 수 있습니다.

## 결과를 어떻게 쓰나

- **FAIL**: 해당 부품을 바꾸거나, 그 부품에 맞게 레시피를 고쳐야 합니다.
  예를 들어 BMP280이 왔다면 습도를 쓰는 레시피는 쓸 수 없습니다.
- **WARN**:
  - BME280이 0x77에서 응답하면, 레시피의 `bme.begin(0x76)`를 바꾸라는 안내가 필요합니다.
  - MPU6050 대신 MPU6500이 왔다면 대부분 동작하지만, 레지스터가 다른 기능은 확인해야 합니다.
- **흔들림(σ) 값**: 시뮬레이션 잡음 시험(`wokwi/variants/*--jitter`)이 실제 센서의 흔들림을 흉내 내는 크기의 근거가 됩니다.
  기록된 값이 시험값보다 크면 잡음 시험의 폭을 넓혀야 합니다.
